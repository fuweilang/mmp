## 缺陷（按严重度）

### F1（P1，修了但没修全）sms-login 仍可枚举手机号
- 位置：`ground/apps/backend/src/auth/auth.service.ts:264-271`（268 只统一了「用户不存在/停用」，269 `consume()` 的错误直出）
- 实际：同一请求形状（`{phone, smsCode:"654321"}`）三种响应文案不同 → 攻击者可判定号码是否注册、甚至是否有活码。
  ```
  未注册号        => 400 {"message":"手机号或验证码错误"}
  已注册号 无活码 => 400 {"message":"验证码不存在或已过期"}
  已注册 有活码   => 400 {"message":"验证码错误"}
  ```
- 预期：三者统一为同一文案（与 `:268` 一致）。
- 修法：`openSmsSession` 内 `try { await consume } catch { throw new BadRequestException('手机号或验证码错误') }`；如需保留「尝试次数过多」，改为按 phone+IP 计数命中后才提示，且该提示也不得区分号码存在性。

### F1b（P3，同类残余）发码静默路径有耗时差
- 位置：`sms.ts:178-183` 静默分支只 1 次查询即返回；正常分支 3+4 次查询并可能发真实短信。
- 实测（mock，无网络）：静默 3.64ms vs 落库 7.97ms（生产 + 腾讯 HTTP 差距更大）。
- 修法：静默分支补等价 DB 写（插入后 `discard`）以拉平；文案已一致，列为残余侧信道即可。

### F2（P1/需产品决策）client-register legacy 可绕过短信验证
- 位置：`dto/login.dto.ts:44-48`（`smsCode` 可选）→ `auth.service.ts:58-62`（无码走 legacy，仅审计打标）
- 实际：无需任何验证码即可 `POST /api/auth/client-register` 建企业管理员账号并返回 7 天 JWT；等于 `/auth/register` 的短信门槛形同虚设（攻击者只会用 client-register）。同时可抢注他人未注册手机号。
- 预期：要么关闭 legacy，要么 legacy 建号后进入「未验证」状态，禁止持有 console 权限直到 Web 端补验。
- 修法：给 `user` 加 `phoneVerifiedAt`（或复用 status=pending），legacy 建号置未验并在 `establishSession`/`toMe` 拦截；最少也要对 legacy 建号限流+禁止 admin 权限。

### F3（P3）并发注册失败方返回 500 而非 409
- 位置：`auth.service.ts:114-115` 预检查在事务外，`130-136` 事务内 `user.create` 撞唯一键
- 实测：`ok | rejected:PrismaClientKnownRequestError`；经 `ApplicationExceptionFilter` → 500「服务暂时不可用」（`status>=500` 统一文案）
- 修法：`createEnterpriseAccount` 的 `$transaction` 外包 `try/catch` 把 P2002（以及 slug 冲突）映射为 `ConflictException('手机号已注册'/'品牌已被占用')`。

### F4（P3）并发 consume 的失败文案与设计不符
- 位置：`sms.ts:246-251` + `auth.service.ts:207-211`（`findLatest` 先过滤 `consumedAt:null`）
- 实测第二个请求报「验证码不存在或已过期」而非「验证码已使用，请重新获取」。仅文案，不影响原子性。

### F5（观察，不算本次 10 项）proxy-common.conf 被改但未写入修复报告
- `infra/production/proxy-common.conf:8-11`：`proxy_buffering off; proxy_cache off; proxy_read_timeout/send_timeout 3600s`（原 120s），作用于 **所有** Ground API location。`nginx -t` 通过、无重复指令（location `/` 用的是 `proxy-common-long.conf`，未被改动）。需李庚确认是否本意（长回答流式）；副作用是 API 连接可挂 1 小时。

### F6（观察）手机号 5 次/小时在突发下不可达
- 60s 冷却 + 部分唯一索引使同一 phone+scene 每分钟最多 1 行，实测连发 6 次（换 IP）全部 `ok`（后 5 次为冷却静默）。防轰炸实际由冷却承担；限额只在跨 25 分钟以上连续请求时触发。非缺陷，但与「5 次/小时」的描述不一致。

### F7（观察）CI 未接 test:auth
- `ground/.github/workflows/ci.yml:51-71` api job 仅 `pnpm verify-api`，且触发分支不含 `5.0`。原报告的「权限拒绝」属实。

## 剩余风险

- `NODE_ENV=production` 是 fail-closed 的唯一开关（`Dockerfile.api:27`、`compose.yml:25` 均已设）。若绕过镜像手工 `node dist/main.js` 且不设 `NODE_ENV`，mock 短信通道重新打开。
- `TRUST_PROXY` 若被设成 `true` 或大于实际跳数，客户端伪造 XFF 左侧可污染 `req.ip`（`main.ts:52-53`）；默认 1 跳正确。
- legacy `client-register`（F2）未决策前，短信验证在生产可被完全绕过。
- 部分唯一索引脱离 Prisma schema 管理；本次 `migrate diff` 未见漂移，但后续含该表的结构变更仍需人工核对。
- 发码静默成功改变 UX（未注册点「获取验证码」显示已发送、收不到短信），需甜甜文案配合。
