# 资料选择与历史消息展示改造方案

日期：2026-11-09。状态：建议方案，未实施。范围仅限会话中的资料选择、草稿引用、发送及历史展示，不扩展为完整资料库重建。

## 建议结论

对齐 WorkBuddy 的交互结构：独立资料选择弹窗，选择后在输入框显示文件标签，发送后历史消息显示文件卡片与用户原话。资料正文、引用定位和模型使用说明进入独立的模型上下文路径，不与用户可见文本混用。

采用结构化、可持久化的资料引用。不能仅靠 CSS 折叠正文，也不能把正文删掉后只给模型一个无法读取的文件名。

## 二、猛犸当前两个问题的原因

### 选择器

`packages/client/ui-enterprise-library/src/client/index.ts:110` 注册通用 `popupSelect`，拉取个人与共享资料后合并为扁平选项。没有文件类型图标、资料目录导航和元数据列。

`ui-commands/src/client/PopupSelectView.module.css` 的 `.card` 以 left/right 0 铺满输入框；file-picker 只增大行距及字号，没有改变通用菜单结构。未就绪条目同时设置 badge 与 detail，且两者可能都显示“还不能用于 AI”，对应截图中的重复文案。

### 历史消息

当前链路：

```text
资料文件标签
 → ui-enterprise-library 的 codec.serialize
 → fetchLibrarySource(..., 'prepare')
 → librarySourceText：来源链接＋模型使用说明＋JSON 摘录
 → serializeDraftPrompt 用展开文本替换标签
 → facade/defaultSink/sendSession 仅传递展开后的文本
 → user/message 的 text
 → MessageItem.contentParts
 → UserContent 的文本气泡
```

源码：`ui-enterprise-library/src/client/index.ts:192`、`selection.ts:117`、`ui-conversation/src/client/input/prompt.ts:57`、`facade.ts:763`、`service.ts:235`、`ui-chat/src/client/chat/MessageItem.tsx:20`。

因此问题发生在发送数据建模阶段。发送后已经没有与展开正文等价、可供历史展示直接复用的结构化资料引用。当前 API 返回的是存储摘录，可能很长，但不保证是完整文件正文；方案不能将“选中资料”描述成“模型已经通读整个文件”。

猛犸已有 `ui-chat/src/client/chat/UserContent.tsx` 的文件卡片，可复用视觉规范；现有普通文件依赖上传回执，资料库文件不能冒充一个已经上传的本地附件。

## 三、交互方案

### 1. 独立资料选择弹窗

- 从“＋ → 资料库”打开居中弹窗，桌面目标 800 × 640，受当前窗口可用宽高限制；小窗口自适应。
- 顶部“选择资料”、关闭按钮；搜索框与“最近使用 / 我的资料 / 企业共享”标签。
- 最近使用和搜索结果用列表；个人与共享资料允许展开文件夹。文件夹用于导航，不自动选中所有子文件。
- 行高以 48px 为基线；左侧复选框＋20px 类型图标，右侧文件名和元数据。窄窗口逐步隐藏次要列，完整名称可查看。
- 未就绪资料置灰，原因只显示一次；区分解析中、解析失败、不支持引用，不能一律写“还不能用于 AI”。
- 底部左侧“已选 N 项”，右侧“取消 / 添加到对话”；零项禁用确认。搜索、换标签或翻页保留选择，不按文件名去重。
- 确认前保持弹窗内部临时选择；取消不修改草稿。确定成功只加入草稿，不发送；添加失败明确提示，不能静默丢失。
- 搜索采用现有名称搜索能力；不在本任务中承诺全文、语义检索。分页、请求取消和陈旧响应隔离与现有接口对齐。
- `@` 保留轻量检索入口，与弹窗共用资料身份、去重及引用行为，无需每次输入 @ 都弹出大窗口。

### 2. 输入框内的文件标签

- 文件图标＋文件名＋移除按钮，保留用户正在输入的提问。
- 点击名称预览所选版本，移除只影响当前草稿。
- 来源按 nodeId 与 versionId 标识；同名不同文件不合并。再次选同一资料时只保留一个有效选择，更新版本须明确替换。
- 切会话和重开草稿后引用仍能恢复；界面不出现正文、JSON 或内部模型提示。

### 3. 发送后的历史消息

文件卡片在用户文本气泡上方，沿用现有普通附件的排列方向与样式。

```text
┌──────────────────────────────┐
│ 文档图标  Slogan大师.docx      │
│ 资料库 · DOCX                 │
└──────────────────────────────┘
看一下我选择的文件，给我做个分析。
```

- 多文件横向自动换行，较多时折叠并提供“展开 N 个文件”；展开只显示文件列表，不展开正文。
- 文件卡片点击打开原先所选的版本。版本信息可置于详情，避免占据主要视觉。
- 用户气泡保留用户原话。复制、编辑后重发、发送中、队列、失败重试与最终历史采用相同投影。
- 复制消息输出文件名/引用链接和用户原话；不混入隐藏摘录。导出会话也采用该规则，内部原始会话日志另行保留其原有用途。
- 删除或撤权后仍保留历史文件名称与提问；访问显示来源不可用，不偷偷切到最新版本。

## 四、实现方式与取舍

| 路线 | 结果 | 建议 |
| --- | --- | --- |
| 只美化通用菜单、折叠大段文本 | 界面暂时变短；复制、重开、队列仍可能暴露展开正文 | 不作为最终方案 |
| 专用选择器＋结构化引用＋独立模型上下文 | 两处问题一起解决，历史回放与模型读取可分别验证 | 推荐 |
| 完整引入 WorkBuddy 式资料技能、按需工具读取与新检索体系 | 改变模型取资料的机制，涉及更多产品与运行时行为 | 后续独立评估 |

推荐路线不要求先建设新的资料库编辑器、协作平台或搜索系统。

### 资料协议

下面是拟议语义，不是仓库已经支持的 API。正式实现时由现有协议所有者定义类型与兼容版本，不能在 UI 私加未知字段。

```ts
type LibraryReference = {
  nodeId: string
  versionId: string
  nameAtSend: string
  mimeType?: string
  sizeBytes?: number
}

type LibraryQuestion = {
  userText: string
  references: LibraryReference[]
}
```

主原则：用户原话与文件引用在提交、Host 接受、队列、会话日志及回放中均保留。显示名称快照用于历史展示，不是授权依据。

### 模型读取路径

首版保留已有版本读取、真实 locator、摘录截断标记及引用规则。Host 接受请求时按当前用户、租户和权限解析引用，再把实际读取的内容作为独立、有持久证据的来源上下文交给模型；文档内容按不可信资料处理。

不将正文塞进 `userText`，也不只在 React 状态存一份干净文本。模型可见上下文必须遵守仓库会话事件/回放规则，保证重启、分叉和重试仍能说明当次读到的版本与内容。具体采用专用资料引用块及关联上下文事件，还是扩展现有附件来源适配器，需要在实现第一步核对协议校验、事件准入、投影与格式迁移。禁止直接把新块强转成旧 `file` 或 `text` 规避校验。

权限失效、版本读取失败或解析未完成时，明确指出具体资料，保留草稿和文件引用供重试。默认不静默漏掉某个文件后继续发送。模型回答中的来源链接继续保留。

### 改造落点

| 层 | 拟修改范围 |
| --- | --- |
| 资料库前端插件 | 独立 LibraryPicker、选择状态、元数据行、草稿引用；共用 @ 与面板入口 |
| 通用命令框架 | 仅增加专用弹窗的接入契约；保留其他 popupSelect 行为 |
| 输入提交 | `prompt.ts`、`facade.ts`、`hub.ts`、`service.ts`，将用户文本、资料引用和上下文分开 |
| Host / API / 会话协议 | 资料准入与权限校验；持久化引用及上下文关联；兼容版本与回放 |
| 历史消息 UI | `MessageItem.tsx`、`UserContent.tsx`，复用附件视觉，增加资料引用的打开行为 |
| 复制、编辑、队列、导出 | 使用同一用户消息投影，避免不同入口重新显示展开正文 |

不能只改 `ui-enterprise-library` 一个插件，也不能只在共享 PopupSelect 上堆资料专属逻辑。新组件遵守现有 slots、store 和注入边界。

## 五、旧消息兼容

新消息从上线起按新协议保存。旧记录分两类：

1. 有可验证的引用身份、来源边界和用户原话：运行只读兼容投影，显示文件卡片与原话，不重写原始日志。
2. 只剩混合文本、无法无歧义恢复原话或资料边界：先保持原文或提供明确标注的“旧版资料内容”折叠区，不猜测删除任意正文。

用户目标是旧记录也尽可能整洁；能否覆盖全部旧记录，必须用真实历史日志抽样后确定。截图本身不能证明存在可安全分割的完整边界。严禁只通过正则删掉包含 `Library citation` 的整段文字，误删用户亲自输入的内容。

## 六、实施顺序与验收

建议先跑通“一份资料→提问→模型正确读取→重启后文件卡片仍正确”这一条完整链路，再扩展多选与选择器。随后补齐旧记录、队列、重试、复制和导出，最后做桌面视觉验收。

验收重点：

- 截图中的超长文件名不会撑宽弹窗，未就绪文案不重复；多选、切标签、搜索和取消行为正确。
- 选择 Slogan 文档并发送原提示后，发送中、成功历史、会话重开均只展示文件卡片＋原提示。
- 用包含已知唯一答案的测试资料核对模型实际能读到所选版本；只是“界面不显示正文”不算通过。
- 对大文档仍尊重摘录范围；回答不声称通读未读内容，真实来源链接可打开。
- 同名文件、多个文件、版本更新、删除和撤权均有确定行为。
- 发送失败草稿不丢失；重复重试不重复创建消息；队列、steer、编辑重发、分叉回放保持引用。
- 混合普通附件与资料库文件可区分来源；普通上传、图片及其他 @ 来源不回归。
- 复制与导出没有内部 JSON、来源正文或模型说明；旧消息兼容不误删用户文字。
- 窄窗口、长列表、键盘操作、焦点恢复及深浅主题完成实际 UI 验收。

当前完成的是源码对照与方案草案。产品代码、会话格式和生产环境均未修改；上述验收项尚未执行。
