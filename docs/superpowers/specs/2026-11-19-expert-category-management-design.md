# 专家分类管理设计

状态：用户已确认专家方案；后续补充技能分类同样需要管理入口，合并实施。用户要求：后台可新增、改名、排序，专家下拉框和前台分类同步。

## 方案

建议使用独立分类表，后台和前台读取同一份目录。现有 PostgreSQL enum 及各端硬编码无法支持运营任意新增；只改后台下拉框无法满足要求。另一种全量 JSON 配置方案缺少关联约束，不采用。本文件中的交互细节为实现建议，尚未得到用户确认。

## 管理交互

- 在后台“专家配置”页右上角增加“分类管理”按钮，打开管理弹窗。
- 显示名称及顺序；支持新增、行内改名、上移/下移，统一点击“保存”生效，取消不写入。
- 名称去除首尾空白，限制 1–32 字，不允许重复或使用“全部”“未分类”等保留名称。新分类排在末尾。
- 用户补充要求删除：允许删除无引用分类；有关联专家或技能时返回引用数量并拒绝，需先调整归属。界面删除需确认，保存前可取消。
- 权限沿用专家配置的编辑权限，服务端校验并记录审计。
- 保存后后台下拉框、列表筛选和分类名称立即刷新。前台下次请求分类目录时同步，无需逐个专家重新发布；已打开页面在重新进入或刷新后同步，不承诺跨端实时推送。
- 前台筛选保持只展示有已发布专家的分类；尚未分配专家的新分类仍会在后台显示。保留“全部”和“未分类”的现有含义。

## 数据与接口

- 新增分类表，保存不可变 key、唯一名称、sortOrder；新增 key 由服务端生成，与中文名称解耦。
- 原 6 个 key 与名称保持不变，按现有顺序初始化。OfficialAgent.category 从枚举改为分类 key 字符串及关联约束；未设置仍为 null。历史专家归属不变。
- 迁移需检查旧枚举实际引用，不删除其他字段或专家记录；历史版本 JSON 的 key 不做重写。
- 管理接口提供读取目录及批量保存；一次事务执行新增、改名、排序。提交完整目录和版本号，版本冲突时提示重新加载，避免两个管理员相互覆盖。禁止改写已有 key；移除现有 key 代表删除，仅无引用时允许。
- 专家创建、编辑、导入及筛选校验由固定枚举改为目录存在性校验；未知 key 返回明确错误，不能悄悄落入“未分类”。
- 公共分类接口返回按顺序排列的 key/name；广场 facets 扩展名称和顺序元数据，沿用 capability key 作为筛选协议，技能分类逻辑不变。
- 专家卡片、详情及其他分类标签通过目录解析名称，不再依赖固定中文映射。读取失败保留已有数据并提供重试，避免覆盖用户编辑。

## 范围与验证

- 复用现有 Vue/Element Plus 管理后台、NestJS/Prisma 和 React 专家广场。
- 当前工作区已有大量未提交改动，包括分类展示；实施时保留并衔接现有改动，不擅自提交、推送或发布。
- 验证迁移保留旧归属；新增分类可给专家保存并发布；改名后归属不变且各端显示新名称；排序在后台和前台一致。
- 覆盖重复/空白/保留名称、未知 key、越权、并发冲突及保存失败不丢失输入。
- 运行受影响后端和前端测试及构建。数据库迁移先在隔离测试数据库验证；本机可能指向生产 Core，未经核实不得直接运行迁移。
- 交付代码、迁移文件及验证结果。生产迁移和发布另按用户指示执行。

## 用户补充：技能分类

技能配置增加同样的管理入口，专家和技能目录各自独立；保留技能最多 3 个分类及现有归属。技能分类改为可扩展字符串列表，新增、改名和排序同步至技能后台及前台。

用户补充：专家与技能分类均须支持删除。删除已被引用的分类被拒绝，保留所有现有归属；数据库检查引用与目录写入需避免并发产生孤立分类 key。
