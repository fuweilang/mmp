# 完整技能包上传与使用改造方案

日期：2026-11-10。状态：待用户确认设计；未开始产品代码修改。

## 你将得到什么

沿用现有猛犸管理后台与 Agent 运行端。上传一个以 `SKILL.md` 为入口的 ZIP，平台完整保存包里的脚本、参考资料、图片、模板及其他普通文件；选用技能后，运行端取得同一版本的全部文件，模型加载说明并使用现有文件、命令工具完成任务。

“上传后可用”指符合技能包格式、处于容量范围、运行环境具备所需工具与依赖的包，可以直接进入现有技能使用流程。导入成功、技能正文加载成功和任务执行成功分别有实际结果；缺少 Python、第三方库或外部服务授权时明确报告缺什么，不宣称执行完成。

这次目标仍是现有管理端的官方技能上传与分发，不另建普通用户个人技能库或技能市场。

## 方案选择

采用“保留完整文件目录，复用现有 Agent 工具”。这是与已选技术栈、WorkBuddy 调查结论及现有标准会话最相符的路径。

只放开上传白名单无法完成目标：目前资源接口与运行端仍限定 `references/`，脚本到不了执行环境。另建云端脚本执行服务会改变执行位置、权限、文件访问和运维方式，本次目标并不需要它。

云端 NestJS API 负责校验、保存和分发文件；脚本在当前会话所连接的 Agent 运行环境执行。桌面与网页共用同一技能目录和版本，但具体任务仍取决于其已连接的运行环境。

## 你会在哪个窗口操作

| 步骤 | 窗口 | 改造后的表现 |
| --- | --- | --- |
| 1 | 访达 / 文件管理器 | 准备一个技能 ZIP，内部目录保持原样。 |
| 2 | 浏览器：猛犸管理端 → 技能管理 → 新建技能 | 选择 ZIP。系统校验后展示名称、介绍、文件总数、脚本数、参考资料数、素材数及包大小。 |
| 3 | 同一个编辑弹窗 | 核对名称和介绍，点击“保存并启用”。也保留只保存草稿的操作。 |
| 4 | 猛犸客户端 / 已连接运行端的网页会话 | 选择技能与工作区，开始任务。说明按需加载，整个包的文件一起就绪。 |
| 5 | 同一个任务窗口 | 查看文件工具、命令工具的执行结果及生成文件；失败时能看到具体原因。 |

界面保留现有流程，只补齐包内容预览和必要的错误提示，不另加一套脚本控制台。

## 本次要解决的具体问题

| 目前代码的行为 | 改造目标 |
| --- | --- |
| 除 `SKILL.md`、`skill.json` 外，只收 `references/` 或 `resources/`。 | 接受技能根目录内的普通文件，包括 `scripts/`、`references/`、`assets/`、`templates/`、`resources/`、根目录辅助模块、依赖清单与许可证。 |
| `.py/.js/.sh` 等文件类型被拒绝。 | 普通文件按包内容保存；上传阶段不执行程序。 |
| `resources/` 被改名为 `references/`。 | 保留原名、原字节和相对路径，不改写正文里的引用。 |
| 平台会生成或重写包内 `skill.json`。 | 新格式把平台索引放数据库中，保留上传者原有 `skill.json`，避免覆盖脚本可能读取的文件。 |
| 原始 ZIP 与展开文件共用目录，可能和包内 `package.zip` 重名。 | 新格式将展开目录与原始上传归档分开放置。 |
| 运行端仅下载参考文件，且总量上限与上传端不一致。 | 完整清单中的每个文件都下载、核验并保存，上传端和运行端执行同一容量规则。 |
| 模型只能得到说明与有限附件。 | 模型获得说明及完整包的资源根目录，沿用现有读取与命令工具。 |

## 技术栈与责任位置

管理页面继续使用 Vue 3、Element Plus、TypeScript。上传与资源接口继续使用 NestJS、Prisma、PostgreSQL 和现有 ZIP 库。运行端继续使用 `mammoth-agent` 的 Node/TypeScript、技能 Provider、标准会话与文件/命令工具。模型仍走现有猛犸云端配置。

Ground 与 Harness 分别修改自己的代码；不把终端实现搬进 Ground，不修改 WorkBuddy 程序。沿用现有管理员权限、启用/停用、版本固定、审计和模型调用链。

## 包识别与内容保存

1. 接受平铺 ZIP，或带外层目录的单技能 ZIP。以目标技能根目录的 `SKILL.md` 为入口。
2. 如果 ZIP 顶层已有 `SKILL.md`，该根目录就是技能；内部示例、参考资料或子目录中的同名文件作为包文件保留，不额外注册为独立技能。如果没有顶层入口，寻找唯一可确定的外层技能目录。多个独立候选入口报“请选择一个技能单独上传”，不猜测使用哪一个。
3. 解析普通 YAML 元数据，支持多行 description 和普通嵌套字段；只从允许的字段提取展示信息。原 Markdown 全文不改写。YAML 不执行自定义代码，限制别名展开等解析成本，解析失败给出位置或字段原因。
4. 兼容平台已有 `skill.json`。根目录该文件存在时须可解析为 JSON 对象；无法解析时报文件格式错误。对象同时具有自有 `key`、`name`、`description` 或 `summary` 字段，且 entry 缺省或等于 `SKILL.md` 时，识别为平台清单；这些字段按已有平台规则验证，无效时报错，不能退回自动生成标识。其余 JSON 对象作为第三方普通包文件保留，元数据由 `SKILL.md` 推导。无论识别为哪种，完整包原文件都不因后台改显示名称或平台重定向key而被重写。
5. 保存所有普通文件的原始字节。只忽略可明确识别的系统打包碎屑，如 `.DS_Store`、AppleDouble 和 `__MACOSX`。`.git/`、`node_modules/`、虚拟环境等不随技能分发；遇到时明确提示重新打包，不能静默删文件后显示“完整导入”。
6. 对路径进行严格校验：禁止绝对路径、向上跳目录、符号链接和特殊文件；拒绝重复或在 Mac/Windows 上会冲突的路径，以及同一路径既为文件又为目录的包。检查 ZIP 中原始名称，防止解压库先修正非法名称而掩盖问题。
7. 新包使用 `revision目录/content/` 存展开文件，原始上传 ZIP 放在 `content/` 外；数据库 `storagePath` 指向真实展开目录，`sourceZipPath` 指向原始归档。旧包保持已有存储路径，不进行批量搬迁。
8. 平台独立生成文件清单：相对路径、字节数、SHA-256、是否带执行标记，以及对整个排序清单的摘要。校验失败不创建可使用的版本；替换失败不改变当前有效版本。

## 首版容量规则

这是我的实施建议，待本方案确认后固定进契约与配置。保留已有压缩包最大 12MiB、解压后最大 10MiB、主说明最大 100KiB；普通文件数量由 50 提高至 500，单文件可以使用解压总量内的容量，不再因为超过旧的 1MiB 附件限制而拒绝字体或模板。

上传校验、保存、资源下载、运行端展开使用同一组容量数据。规则作为可验证配置及新格式包的明确声明，运行端检查本地可接受额度，发现不一致提前报告，不能导入时通过、下载中途才按另一套默认数值失败。运行端自有上限也明确配置，不盲信远端要求无限分配。

上传解压与下载均在读取过程中累计检查实际字节，不先把无界内容全部读入内存再检查。新增文件清单及响应自身也需要有界；并发下载限制为少量受控任务，不能为500个文件同时建立500个请求。

容量大小可在后续实际样例反馈后调整，本次不将大依赖目录或整个开发仓库直接当成技能包。

## 新旧包、接口和客户端兼容

### 数据库

复用 `officialSkillPackage.manifest` 的 JSON 保存新格式标记及文件清单。新包记录 `packageFormat: 2`、完整 files、包摘要和容量规则。旧包没有这个标记，继续按现有 references 清单读取；不要求重传已有115条技能，也不修改它们固定在旧会话中的 revision。

新格式的 files 是完整可分发文件清单，包含 `SKILL.md` 与用户提供的所有有效普通文件。references 仅表示参考资料分类，不再被当作新格式全量附件清单。

### API

保留现有 `GET /official-skills/:id/content`，新增明确的 `packageFormat=2` 请求能力参数。旧请求读取旧包时返回原有响应，避免现有严格响应校验因新增字段而失败。

新运行端请求新能力。新包响应包含 `packageFormat: 2`、原 instruction、完整 files、包摘要和容量数据；每项文件含 `path`、`bytes`、`sha256`、`executable`。旧包返回已知旧格式，新运行端按显式旧格式路径兼容加载。不得对新包缺字段或损坏时悄悄退成“只加载正文”。

旧客户端请求新格式包时返回明确的“此技能包含完整包内容，请更新客户端”错误；不能只返回其能识别的参考文件并假装加载完成。新版本后端先上线，再更新运行端；设计及实现阶段只进行本地验收。

资源仍通过现有 `GET /official-skills/:id/resources?revision=...&path=...` 获取。服务端以指定版本文件清单做准入检查，移除仅允许 `references/` 的目录假设。不能读取清单外文件。资源作为下载字节返回，使用 `application/octet-stream`、附件响应与 `nosniff`，避免把包内 HTML/脚本在管理站点同源执行。

session 创建接口及现有冻结 revision 的含义保持一致。停用、删除与历史固定版本的读取继续遵循现有 `skillReadDecision`，不借这次改造扩大授权范围。

### 显示信息修改

管理员改名称、介绍和分类只更新平台展示元数据与平台索引。新包原文件、文件摘要和已冻结内容不随之修改。代码中 `syncCurrentManifestMeta`、`retargetPackageKey`、表单构建与 ZIP 替换都必须按格式处理，不能遗漏某个路径继续覆盖原文件。

## 运行端如何真正使用 scripts、references、assets

1. 标准会话仍先获得技能名称和摘要。模型调用现有 `skill(name)` 时，Provider 获取该会话固定的包版本。
2. 新格式先验证清单、文件数量、完整相对路径及容量，再把全部文件下载到所选工作区内的任务专用目录：`.mmp/runtime/skill-packages/<随机会话所有者>/<随机加载目录>/`。使用已解析的真实工作区路径，逐级拒绝符号链接或逃出工作区的路径。此目录不在本地技能自动发现的 `.mmp/skills` 中。运行端通过当前技能查询的cwd确定所属工作区，缺失工作区则明确失败。这项选择避免Linux bwrap 用独立 `/tmp` 遮住宿主临时技能文件，也不需要增加沙箱目录授权。
3. 每个文件下载期间检查实际长度和 SHA-256。正文 `instruction` 必须与清单中的 `SKILL.md` 字节对应；完整清单摘要必须一致。发现丢文件、错误版本或校验不符时清理临时目录并报告，不能缓存半包。
4. 保留 ZIP 提供的执行标记，但只设置当前用户必要的读/写/执行位，不能恢复组/全员写权限或特殊权限。脚本能通过现有解释器调用；带有效执行位和 shebang 的脚本也要覆盖直接调用样例。模板、图片、字体、二进制数据不做文本转码。
5. 返回现有 `resourceBase` 资源根目录和原正文，让相对文件关系可用。标准会话的现有文件、终端工具与权限继续负责动作，不自动在上传或加载阶段执行脚本，也不静默运行依赖安装命令。
6. 日常输出保存到用户选择的工作区。云端固定revision的原包保持不变；运行目录是该会话的执行副本，可以在现有沙箱允许下生成缓存，不与其他会话共享。缓存命中时，重新核对所有声明原文件的长度与摘要；额外生成的缓存文件允许保留，但不成为发布包文件。若原文件被修改或删掉，则取消该目录的缓存资格，重新下载并核验固定revision至新的随机目录。旧执行目录留给可能仍在运行的命令使用，最终随该Provider清理，不边用边覆盖。不以已改写目录冒充原包。工作区切换属于不同缓存键；会话恢复重新准备，不跨会话复用可写副本。
7. 验证实际工具能看到资源目录，包含Linux bwrap 的挂载语义；不能只测试磁盘上文件存在。任务会话释放、Provider销毁、账号切换和加载取消时遵循现有生命周期清理；取消后不能再发布“已就绪”结果。对执行副本的文件权限只作正常运行需要，不能宣称Unix文件权限等同于执行沙箱。
8. 不新增自动云端执行器，不修改 Agent 主循环，不主动关闭或扩大沙箱、网络或工具审批。不把某个技能的 `allowed-tools` 声明视为用户已经授予了这些工具。

完整包索引属于版本数据，本次尽量复用现有会话事件和工具结果记录，不新增 Session 事件格式。文件被实际读取或脚本被执行的结果由现有工具日志记录；若实施中发现必须改变持久化字段，应先按仓库的持久化兼容要求补齐设计与对应测试，不能暗改格式。

## 实施顺序与每一步的交付

确认方案后，使用独立工作目录实施，保留当前工作区内其他任务的修改，不擅自提交或推送代码。

| 阶段 | 主要修改位置 | 可以检查的结果 |
| --- | --- | --- |
| 1. 完整包解析和保存 | Ground `official-skill/skill-package.ts` 及必要的独立包清单/路径校验模块 | 同一个样例包的脚本、资料、图片、模板全部保留，路径和字节核对一致。 |
| 2. 完整文件接口 | Ground `official-skill.service.ts`、`official-skill.controller.ts`、DTO | 指定 revision 能取得全部声明文件；未声明的路径读不到；旧包接口兼容。 |
| 3. 运行端加载 | Harness `official-agent-gallery/src/ground.ts`、`skill-provider.ts`、`index.ts` 的资源路径消费者 | 加载后得到完整资源根目录，校验失败不留下半包，取消和清理有效。 |
| 4. 管理页面 | Ground `AdminOfficialSkills.vue`、`api/admin.ts` | 上传预览能看出包含多少脚本、资料与素材；仍可保存草稿、保存并启用与替换版本。 |
| 5. 实际执行与回归 | 两侧现有测试体系及独立验收样例 | 现有 standard Agent 的真实文件、命令工具读取包内容并执行自制无外部依赖脚本，生成可验证结果；旧功能仍通过。 |

每阶段先增加能暴露当前缺口的测试，确认失败原因，再实现并通过测试。涉及工具输出和真实组合的变更，同时补齐仓库要求的录制会话/快照和 Loader 组合覆盖。实施前的基线失败单独记录，不能算成本次验证通过。

## 验收样例与通过标准

| 样例 | 预期 |
| --- | --- |
| 仅 `SKILL.md` | 可上传、保存、启用、加载，原正文不变。 |
| `references/guide.md` | 模型能用文件工具读取该参考资料。 |
| `assets/` 中图片、模板、二进制数据 | 原字节保留，运行端读取得到相同 SHA-256。 |
| `scripts/` 中自制 Node 脚本 | 脚本读取 references 和 assets，使用现有命令工具运行，在工作区生成含指定结果的文件。无需外部 API。 |
| 自制 Python / Shell 脚本 | 在确有相应解释器的平台实际运行，包含 shebang/执行位样例；没有解释器时显示真实失败，不能记为通过。Windows 使用相应平台可运行样例，不冒充已验其他平台。 |
| `resources/`、根目录 helper、LICENSE、上游 `skill.json`、包内 `package.zip` | 原相对路径与字节保留；与平台索引和源ZIP互不覆盖。 |
| 平台清单与第三方同名JSON | 按固定识别条件分别处理；平台字段无效不换key兜底，第三方文件不被平台重写。 |
| ZIP带外层目录、中文路径、嵌套资料中的 `SKILL.md` | 正确选定主入口，保留有效内容。 |
| 多个独立技能入口 | 提示选择一个技能单独打包。 |
| 脚本缺第三方依赖 | 任务明确指出实际错误与缺少的依赖，上传成功不被误报为执行成功。 |
| 替换新版本后恢复旧会话 | 新会话读取新版；旧会话仍按已有规则读取固定旧revision，不能混合新旧文件。 |
| 下载失败、文件损坏、超容量、取消、账号切换、并发加载 | 无半包成功、无跨会话可写缓存污染，清理与错误反馈符合现有生命周期规则。 |
| 运行后原文件被修改或删掉 | 下一次加载重新准备固定版本；新增缓存可保留但不混入版本文件清单。 |
| Linux bwrap 隔离 `/tmp` | 技能在工作区内准备，实际命令仍可读取和执行；只有Mac验收证据时不宣称Linux已验收。 |
| 越界路径、链接、重复/冲突名称、清单外文件读取 | 在入口或读取执行点拒绝，当前有效版本不被破坏。 |
| 旧客户端访问新格式 | 明确要求更新；现有旧格式技能与会话继续可读。 |

自动集成验收允许用确定性的模型响应驱动真实 Agent/工具，模型和HTTP使用测试夹具时必须明确标注。真实云端模型和真实管理页面逐点击验收另列结果，不能用模拟模型测试替代。部署或客户端发布仍需按实际发布流程执行，本次设计不等于已经上线。
